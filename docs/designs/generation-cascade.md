## Problem Statement

Generated problem sets sometimes fail or come back short of 10. The goal of this
redesign is one thing: **a full, guarded set of 10, every time, inside the route's
300s `maxDuration`, on every tier.** Quality and cost matter, but they are guard
rails in this design. The target is reliability.

The session started as "finish the GPT-5.6 model-comparison eval". It turned into
this because the eval cannot see the failure. It calls each model single-shot, one
problem at a time, with a 4000-token budget, no chunking and thinking set to low
(`scripts/eval-model-comparison.ts:25-35`). The most likely cause of short mid-tier
sets is exactly the condition it removes. Mid tier on Gemini runs
`sonnetChunkConfig` (`lib/generation/problems.ts:312`) with 4-wide chunks, an
Anthropic-tuned `maxTokens` and `thinkingLevel: "medium"`. The Sep 4 probes showed
this reliably returns `MALFORMED_FUNCTION_CALL` (thinking about 50k tokens against a
26k budget, and output alone hitting the ceiling even at LOW thinking).

## Demand Evidence

- The tutor reports real sets that failed or came back short. Failure class:
  reliability, not wrong answers, not calibration, not LaTeX.
- **Rate unknown.** Nobody has read `Session.genMeta` drop reasons to learn how
  often this happens, on which tier, or from which cause. This is the biggest gap
  in the evidence, and filling it is The Assignment.

## Status Quo

No known workaround or rate. The uncommitted working tree contains a symptomatic
patch: up to 4 refill attempts under a wall-clock budget (`nextAskCount`,
`hasTimeForAnotherAttempt`). If a 4-wide Gemini chunk fails deterministically, more
retries spend more money on the same failing call.

## Premises

1. **Metric:** short-or-failed-set rate per tier, plus p95 wall-clock against 300s.
   Measure a baseline before changing anything. Today's `genMeta` can only measure
   part of this (see Instrumentation), so the baseline starts with a small
   instrumentation change.
2. **The rewrite is committed.** It is not gated on beating a targeted fix. The
   user ruled that out. The old pipeline, measured on the same metric, is still the
   "before" column, so a win is demonstrable. The baseline's cause breakdown
   decides the **ladder**, not whether the rewrite happens:
   - If the cause is Gemini `MALFORMED_FUNCTION_CALL`, no Gemini-style chunked
     rung is allowed in.
   - If it's guard drops, the per-rung guards and prompts get the attention.
   - If it's 300s kills, the deadline logic matters most.
   Slot fan-out ships in every case.
3. **Keep the contracts, not the code.** Keep tool-use output, `problemOk` /
   `solutionOk` / `answerOkFor` on the final answer, `tooSimilarToSeed` dedup,
   count=10, the plan stage for non-contest subjects, `genMeta` provenance, and
   "never ship short". Cut workaround machinery the new models don't need.
4. **Models are an eval output.** Which rungs exist, and in what order, is decided
   by measurement. The user's proposed ladder (below) is the starting hypothesis.
5. **The gate has the same shape as production:** full 10-problem runs through
   the real entry point, every tier, several runs per tier, scored on short-set
   rate, latency, $/set, plus the human 1-5 `--rate` so quality can't silently
   regress. The GPT-5.6 single-shot harness is shelved, uncommitted.
6. **Split the working tree first.** The retry/time-budget change and
   `countForTier` → 10 for hard tier are production behavior. They get their own
   commit-or-revert decision and don't ride along with the eval or the rewrite.

## Approaches Considered

- **A: One call per set** (Claude only, one big streamed call per tier). Rejected:
  one bad call still sinks the whole set, and a 10-problem hard stream sits near
  300s.
- **B: Per-problem fan-out.** Kept as the core of D.
- **C: Background generation job.** Deferred. It removes the 300s ceiling but adds
  job state and a polling UI. Revisit only if D's p95 latency is the remaining
  problem.
- **Per-set cascade** (escalate the whole set on failure). Rejected: it loses
  item-level failure isolation, which is the point.

## Instrumentation (before the baseline means anything)

Today's `genMeta` has four blind spots for this metric:
- **No timing.** `GenerationRunMeta` has no duration field, so p95 can't be read.
- **Overwritten on regenerate.** It's one row per session, and a tutor retrying
  after a failure erases the failure record.
- **Nothing on a 300s kill.** The route writes `genMeta` only when
  `generateProblems` returns.
- **Coarse failure reasons.** `generation-failed` doesn't separate
  `MALFORMED_FUNCTION_CALL` from other causes, except in a free-text excerpt.

The small fix, shipped on the legacy pipeline first:
1. Add `startedAt`, `wallTimeMs` and a structured `finishReasons` count per stage
   to `GenerationRunMeta`.
2. Before generation starts, the route writes a `{ status: "started", startedAt }`
   marker. A run whose status is still `started` well after 300s counts as a kill.
3. On each new run, the previous run's summary (tier, kept, status, wallTimeMs,
   top drop reasons) moves into a capped `genMeta.prior` array (last 5). A retried
   failure then stays countable. This is a read-modify-write on a `Json` column, and
   the per-user semaphore allows 2 concurrent runs per instance, so two
   simultaneous regenerates of one session can lose a `prior` entry. That's an
   accepted undercount for a diagnostic. Move to a version column only if it ever
   gates behavior.

`genMeta` can't be filtered in SQL (`queryRaw` is banned), so the baseline script
loads the user's sessions from the window with `genMeta` set and aggregates in
app code.

## Recommended Approach: D, per-slot cascade fan-out

### Shape

1. **Plan** (unchanged role). `planFor` settles tier, rubric, answerFormat and
   competition exactly as today.
2. **Slots.** A slot is the unit of work, `{ index, subtopic?, seed?, role }`,
   where `role` is `variant-source` (hard adapt path) or `calibration` (a
   difficulty example, as anchors are used on scratch today). Launch 13 up front,
   and keep a **reserve pool** of at least 7 more slot specs for replacements
   (item 4). Construction by plan source:
   - **Corpus fast path (no model call).**
     - Hard tier: fetch `getAnchors` with `count + 10` seeds. Each slot gets its
       own distinct seed as `variant-source`.
     - Easy/mid: slots share the anchor set as `calibration`, and each gets its own
       `index` plus a distinct category/number-band hint drawn round-robin from the
       anchors.
   - **Model plan.** `emit_plan` gains an **optional** `slots: string[]` of
     distinct subtopics (at least 20). The lesson path ignores it.
   - **Fallback plan, or a model plan with too few slots.** Deterministic: the
     topic plus an index hint ("problem 7 of 20, a different sub-skill from the
     others"). Items already kept are fed back as the existing `avoidStatements`
     on every later launch.
   - Diversity comes from slot design plus `avoidStatements` plus dedup, because
     no call sees the whole set.
3. **Ladder per slot.** Each slot runs independently up the rungs:
   `DeepSeek V4.1 → GLM 5.3 → Claude Opus 5.5` (starting hypothesis, IDs
   unconfirmed). A rung produces one problem through a forced tool call. A slot
   escalates to the next rung on any of these:
   - a malformed or missing tool call, a filtered finish, or an API error
   - a timeout at the rung's deadline (below)
   - `problemOk`, `solutionOk` or `answerOkFor` failing
   - a hard-tier solver disagreement (below)
   A slot that fails the last rung is dropped with its reasons.
4. **Assembly.** As slots pass, keep them in arrival order, deduping each new item
   with `tooSimilarToSeed` against items already kept.
   - A duplicate re-runs its slot once at the same rung, with the kept statements
     in `avoidStatements`. A second duplicate **escalates** the slot, like any
     other guard failure.
   - When 10 are kept, abort in-flight slots (`AbortController`) so their spend
     stops.
   - **Replacement:** when a slot exhausts every rung while `kept + in-flight < 10`
     and the deadline still allows an Opus rung, launch a replacement slot from the
     reserve pool.
   - Fail loudly, exactly as today, only when the reserve pool is empty or the
     deadline leaves no room for another Opus rung.
5. **Deadlines.** Every rung call has a per-call timeout `T_rung` (cheap rungs start
   at 60s, Opus at 120s for easy/mid and 150s for hard). Before starting a rung, a
   slot checks `remaining = 300s − elapsed − 15s` (a route/persist reserve). A cheap
   rung starts only if `remaining ≥ T_cheap + T_opus`, and Opus only if
   `remaining ≥ T_opus`. Otherwise the slot jumps straight to Opus, or stops. These
   are placeholders, and the spike's measured p95 per rung replaces them.
6. **Hard tier (adapt path).** A rung writes the variant **and** its full solution
   in one call, so `seed-sketch` and `expand` go away. The solver (`solve.ts`,
   Claude) then checks the answer.
   - Disagreement now **escalates the slot** instead of overwriting the answer.
     That removes the "solve before expand" ordering constraint entirely.
   - With open-weight writers, the solver is cross-family again. Only an
     Opus-rung item gets Opus-checks-Opus, which is today's accepted posture.
   - Escalation stays per problem: one solver call per rung per slot. Below the
     top rung, a disagreement escalates. **At the top rung**, where there's nowhere
     left to escalate, keep a small version of today's majority vote: up to 2 more
     solves, and keep the item if a majority agrees with the writer's answer
     (otherwise drop it). A solver false negative at the top then doesn't turn
     straight into a short hard set. The dropped slot is replaced from the reserve
     pool, subject to the deadline.
7. **Easy/mid correctness.** v1 keeps today's posture: no solver on the scratch
   path, and `answerOkFor` on the final answer. Cheaper writers raise the risk of
   a confident wrong answer that passes every guard, and the cascade cannot
   escalate on what it cannot detect. So the eval's human `--rate` pass must
   explicitly check answers on a sample. If the wrong-answer rate rises against
   baseline, a correctness check becomes a v1.1 requirement (see Open Questions).
8. **Provenance.** `genMeta.problems` gains per item `{ slot, rung, model,
   escalations[] }` and per run `{ slotsLaunched, slotsAborted }`. Add drop reasons
   for `rung-timeout` and `slot-exhausted`, keeping the closed-vocabulary rule in
   `gen-meta.ts`. `pricing.ts` gets rows for every rung before cutover. The
   `pricing-silently-drops-gemini-stages` learning applies: an unpriced rung must
   show as `unpriced`, never be summed silently.
9. **Concurrency.** 13 parallel slots per request, with most of them on the first
   rung. Put a per-vendor semaphore in front of each rung, following the
   `rate-limit.ts` pattern. It is **per instance only**, and Vercel spreads
   requests across instances, so it can't enforce an account-wide limit. Size it
   at roughly the vendor's account concurrency limit divided by the number of
   concurrent generate requests expected (1–2 for one tutor). Treat a vendor 429
   as an escalation trigger, not a failure.

### Rollout

Phasing (ordering only; the ladder design is unchanged):
1. Instrumentation, then the baseline read.
2. Slot fan-out with a **known-good ladder first**, e.g. Sonnet 5 then Opus 5.5.
   That tests the reliability mechanism (isolation, replacement, deadlines) with
   no new vendor.
3. Open-weight rungs (DeepSeek, GLM) go in front once the spike and the hosting
   decision clear. Each one's pass rate is measured against the ladder from step 2.

Then:
- Build the new pipeline behind `GENERATION_PIPELINE=cascade|legacy`, default
  `legacy`. Legacy stays the baseline and the instant rollback.
- The eval reuses `scripts/eval-generation.ts` rather than adding a new harness,
  since it already calls `generateProblems()` and has `--compare` and `--rate`.
  Its gaps: it runs fixtures once each, sequentially, with its own client, and
  records no timing. Extend it with:
  - `--repeat N` (N ≥ 20 per tier)
  - `--concurrency K` to exercise real fan-out against vendor limits
  - `wallTimeMs` recorded from the same `genMeta` field the route writes
  - short-set rate, p95, $/set and pass rate per rung, by tier
  Run it once with each value of the flag. The route's own overhead is excluded,
  which is what the 15s reserve in the deadline rule covers.
- Cut over when the cascade's short-set rate is at or below the baseline's (target
  0 across the run), p95 is under 300s with margin, and `--rate` shows no quality
  regression. Then delete the legacy path and rewrite CLAUDE.md's generation
  section in the same change.

## Open Questions

- **Do the rungs exist as described?** "DeepSeek V4.1" and "GLM 5.3" model IDs,
  forced tool-calling support, output ceilings, pricing and latency are all
  unconfirmed. This is a blocking spike.
- **LaTeX fidelity per rung.** Gemini's JSON mode silently dropped `\b` from
  `\binom`. Every rung must pass the same escape stress test before admission
  (`\binom`, `\frac`, `\theta`, `\nu`, `\right`, `\tau`, `\forall`). A rung that
  corrupts silently is disqualified, not escalated past.
- **Hosting and student data.** Is it the vendors' own APIs (servers in China) or
  a US inference host (Together, Fireworks, OpenRouter)? Every prompt contains
  student profile text. Decide before the spike picks an endpoint.
- **Easy/mid correctness check.** If the eval shows cheap rungs shipping more wrong
  answers, what is the check? The Sep 5 finding (solver mostly `unverified` on
  scratch tiers) means "just run the solver" is not free or proven.
- **Is the cheap rung worth it at all?** If most slots escalate past rung 1, the
  cascade costs more and runs slower than Opus-only. The eval should report the
  pass rate per rung. A rung whose pass rate falls below a threshold that makes it
  pay for itself comes out of the ladder.
- **Scope drift from CLAUDE.md.** "Any ML beyond the single generation call" is
  listed as a non-goal. The pipeline already stretches it. This design is a
  deliberate, user-requested redesign of generation, so record it as that in
  CLAUDE.md at cutover.

- Cascade, on an `eval-generation.ts` run with at least 20 full sets per tier (60

  - $/set reported per tier, with no `unpriced` rungs

  - pass rate per rung reported

- Hard-tier feasibility: top-rung solver votes run in parallel (worst case 1 × solver timeout). Hard `T_opus` is 120s. `gen:check` computes feasibility per tier from the ladder config and fails unless at least one complete path (writer + verification + 15s route reserve) fits in 285s. Replacement candidates are launched only while `elapsed < deadline − (T_top + T_solve)`. A unit test asserts at least one feasible full path per tier and rejects a top-rung start with writer-only headroom.
- Rung and solver clients use `maxRetries: 0` and a per-request `{ timeout, signal }`. The call cap counts physical attempts, and the budget reserves calls for uncovered objectives before speculative candidates.
- One absolute request deadline and one `AbortSignal` are threaded through planning, retrieval, semaphore acquisition, writers and solvers. Permits are cancellable, and admission is rechecked after acquiring a permit. After abort, late completions are never published and cause no unhandled rejection (tested with the fake provider and an injected clock). Aborted usage is recorded as `unknown`.
- `genMeta` is split into `published` (bound to the problems currently on the session; the only source for grading's `answerFormat` in `lib/worksheet.ts`) and `attempts` (telemetry: `started`/terminal, runId, `finishReasons`, rungs, capped `prior`). The failure path never writes `published`. Publishing is a conditional update keyed on runId, and a stale run discards its result. CRITICAL regression test: a failed regenerate leaves the old set's grading `answerFormat` unchanged.
- `/api/generate` and `/api/generate-lesson` both re-read and merge `genMeta` at write time. CRITICAL regression tests: regenerate after a lesson keeps `lesson`; a lesson after regenerate keeps `published` and `attempts`. The v2 reader deploys before any v2 writer.
- The scheduler is a pure state machine with an injected clock: exactly 10 objectives, candidates owned by an objective, scheduling by uncovered objectives. A duplicate launches a replacement candidate with a different hint (not an escalation). Dedup happens at keep time, after verification. An objective with no remaining seeds or rungs fails the set loudly, naming the objective. This supersedes the earlier "grace window" wording.
- Strict-band seed retrieval for variant sources: never widen the difficulty band, widen category first, and record widening in `genMeta`. Specified behavior for fewer than 10 suitable seeds, zero seeds, and seeds without solutions (each a named, tested outcome).
- The solver keeps individual observations. Outcomes are:
  - majority-agree → keep;
  - an unresolved disagreement → replace the candidate;
  - a transport error with no prior disagreement → keep, marked `unverified`;
  - a transport error after a disagreement → reject;
  - a request-wide provider outage → `provider-unavailable`.
